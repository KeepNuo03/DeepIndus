## 1. 当前问题判断（与你的分析对齐）

你提出的 5 点判断是准确的，当前确实存在：

1. 业务理解面偏窄，主要集中在 `workbench` 数据。
2. 对话全量落库后，长会话会带来查询与存储压力。
3. Android 端 Agent 业务尚未接入。
4. 中后期需要引入 RAG 提升复杂问答能力。
5. 上游模型（Kimi）拥塞时，可用性波动明显。

## 2. 补充问题（必须纳入计划）

除上述 5 点外，建议增加以下约束与风险管理项：

- 权限与数据边界：跨模块工具扩展后，必须保证按用户/角色/客户端隔离。
- 可观测性深度不足：目前已有审计与工具调用落库，但缺少聚合指标告警（失败率、延迟、超时）。
- 成本治理缺位：尚未建立 token 成本、重试放大、长会话成本上限策略。
- Prompt/工具策略仍偏静态：scene 路由规则需要与新业务模块同步演进。
- 回归测试矩阵不完整：新增模块工具后需要自动化回归，避免答非所问或越权。

## 3. 目标与原则

### 3.1 目标
- 将 Agent 从“workbench 问答”升级为“覆盖关键业务域的数据助手”。
- 在保证稳定性的前提下，支持长对话与可追溯审计。
- 形成可持续演进路径：P0/P1 先工具化，P2 再引入 RAG。

### 3.2 原则
- 先稳定再扩展：先补可用性和容量防护，再扩业务范围。
- 先结构化再智能化：优先工具化/结构化数据，RAG 作为增强层。
- 先可观测再优化：每个阶段都要有可验证指标与回归用例。

## 4. 分阶段实施计划

## Phase A（当前冲刺，1-2 周）：稳定性与容量治理

### A1. 模型可用性增强（后端）
- 增加指数退避重试（只针对可重试错误，如 overloaded/timeout）。
- 增加可选 fallback 模型配置（主模型失败后自动降级）。
- 增加用户级并发闸门，避免单用户并发流式请求打满配额。

### A2. 长会话治理（后端 + DB）
- 会话详情接口改为分页拉取消息。
- 限制单条消息最大长度（超长截断并标记）。
- 设置会话历史窗口（模型上下文只使用最近 N 轮）。
- 建立归档/清理策略（如 90 天冷数据处理）。

### A3. 验收标准
- `AGENT_MODEL_OVERLOADED` 场景下，前端不再长时间卡在“思考中”。
- 会话详情接口在高消息量会话中响应时间稳定（定义目标 P95）。
- 落库量可观测（有统计 SQL/监控面板）。

## Phase B（核心扩展，2-4 周）：业务工具覆盖升级

### B1. 新增工具域（按优先级）
1. 检测记录（趋势、异常样本、缺陷分布）
2. 数据大屏核心指标（当日/周期指标、同比环比）
3. 生产线（线体状态、节拍、异常聚合）
4. AI 模型管理（版本、发布状态、效果指标）

### B2. 编排策略升级
- 将 `scene + 关键词` 路由升级为 `scene + 意图 + 权限` 三元策略。
- 对每个工具增加参数校验与越权拦截。
- 对关键问答增加“必须引用工具数据”约束。

### B3. 验收标准
- 针对上述 4 个业务域分别提供 10+ 条验收问句。
- 回答中能引用结构化数据依据，不再泛化话术。
- 越权问答返回明确错误码和提示，不泄露数据。

## Phase C（Android 接入，2 周）：双端闭环

### C1. Android 端落地
- 新增 Agent API 与流式渲染 ViewModel。
- 在工作台、上传状态、复核详情等页面注入场景化上下文。
- 对 SSE 中断、重试、错误态做 UI 兜底。

### C2. 验收标准
- Android 与 Web 输出语义一致，差异仅限展示层。
- 弱网/断网/超时场景有明确用户提示与重试策略。

## Phase D（中后期，4+ 周）：RAG 增强层

### D1. RAG 范围
- 先做“轻量 RAG”：业务文档 + 历史问答摘要检索。
- 再升级为“标准 RAG”：向量索引 + 增量更新 + 召回评估。

### D2. 记忆策略（推荐）
- 原文日志：完整落库用于审计。
- 运行上下文：最近 N 轮 + 会话摘要。
- 检索记忆：按需召回相关历史，不全量拼接。

### D3. 验收标准
- 长会话中回答一致性提升（上下文遗忘显著下降）。
- 单次请求 token 成本可控，延迟不显著上升。

## 5. 任务拆解与责任分工

- 后端（你当前职责）：Phase A/B/D 主体实现，含工具、编排、容量与审计。
- Android（你当前职责）：Phase C 全量实现与联调。
- PC 前端同事：Web 展示与交互，配合排障面板/trace 展示。

## 6. 风险与预案

- 上游模型波动：重试 + fallback + 限流 + 熔断。
- 工具扩展导致慢查询：索引优化 + 查询分页 + 预聚合。
- 会话增长导致存储膨胀：生命周期策略 + 归档 + 摘要替代全量上下文。
- 跨模块答非所问：强制工具证据引用 + 回归题集。

## 7. 立即执行清单（现在就做）

按优先级执行：

1. 先完成 Phase A（稳定性与容量治理），避免后续扩展时放大风险。
2. 再进入 Phase B 的前两域：`检测记录` + `数据大屏`（价值最高，最能体现 Agent 能力）。
3. 通过验收问句回归后，再扩 `生产线` 与 `AI 模型管理`。
4. Android 接入并行准备，但以 Web 后端稳定为先。

## 8. 当前结论：我们现在应该做什么

现在最应该做的是：

- **先做 Phase A 的 A1 + A2**（模型重试/降级 + 长会话治理）；
- 然后立刻进入 **Phase B 的“检测记录 + 数据大屏”工具扩展**。

这是当前“稳定性、价值、交付速度”综合最优路径。
