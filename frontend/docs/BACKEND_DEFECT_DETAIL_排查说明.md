# 缺陷详情接口「服务器错误」后端排查说明

## 现象

在**记录管理**页面点击某条记录的「详情」后，弹出「服务器错误」。前端会请求缺陷详情接口，若后端返回非 200 或抛出异常，则会显示该提示。

## 前端已做的修改（可先联调验证）

1. **优先传数字 id，其次 detectionNo**  
   前端从记录管理列表点击「详情」时，**优先使用 `record.id`**（数字主键），若没有再用 `record.detectionNo`。  
   因此后端 `GET /defect/:id` 收到的 **多为数字**（如 `12345`），少数为带 `#` 的字符串（如 `#DET-2026A01`）。  
   若 id 含 `#`，前端会做 `encodeURIComponent`，请求示例：`GET /v1/defect/%23DET-2026A01`，后端需对路径参数 **decode** 后再查库。

2. **响应结构兼容**  
   前端已兼容两种返回格式：  
   - `{ code: 200, data: { id, detectionNo, ... } }`  
   - `{ code: 200, data: { data: { id, detectionNo, ... } } }`（多一层 data）

## 请后端重点排查

1. **路径参数是否正确解码**  
   - 请求示例：`GET /v1/defect/%23DET-2026A01`  
   - 路由应拿到解码后的 `#DET-2026A01` 再查库，避免按字面 `%23DET-2026A01` 或空串查询导致 500。

2. **id 类型与查询方式**  
   - 若详情接口按「检测编号」查：用解码后的字符串（如 `#DET-2026A01`）查对应表字段。  
   - 若按数字主键 id 查：需确认列表接口 `GET /records/query` 返回的每条记录里是否有数字 `id`，且前端传的是该 id（当前前端优先传 `detectionNo`，无则传 `id`）。

3. **500 错误的具体原因**  
   - 查服务端日志中该请求的堆栈与错误信息（如：空 id、未解码、查库不存在、类型转换异常等）。  
   - 建议对「记录不存在」返回 404 并明确 message，而不是 500，便于前端区分展示。

4. **响应格式**  
   - 成功：`code: 200`，`data` 为缺陷详情对象（含 `id`、`detectionNo`、`serialNo`、`type`、`confidence`、`timestamp`、`processRecords`、`similarDefects` 等，见 `API_SPECIFICATION.md`）。  
   - 失败：`code` 非 200，`message` 会由前端直接用于弹窗提示（如「服务器错误」即来自后端返回的 `message`）。

## 建议的联调步骤

1. 前端在「记录管理」点击「详情」，在浏览器 Network 中查看请求 URL（应为 `GET /v1/defect/xxx`，其中 xxx 为编码后的 id）。  
2. 后端确认收到请求后，路径参数解码是否正确、用该 id 能否查到记录。  
3. 若仍返回 500，根据服务端日志定位空指针、类型错误或查询条件不匹配等问题，并区分 404（记录不存在）与 500（服务器异常）。
